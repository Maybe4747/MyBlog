# 数据库设计文档

## MySQL 数据库表结构

### 1. users 表 (用户基础信息)
```
+----------------+--------------+------+-----+-------------------+----------------+
| Field          | Type         | Null | Key | Default           | Extra          |
+----------------+--------------+------+-----+-------------------+----------------+
| id             | int          | NO   | PRI | NULL              | auto_increment |
| username       | varchar(50)  | NO   | UNI | NULL              |                |
| email          | varchar(100) | NO   | UNI | NULL              |                |
| passwordHash   | varchar(255) | NO   |     | NULL              |                |
| avatar         | varchar(255) | YES  |     | NULL              |                |
| createdAt      | timestamp    | NO   |     | CURRENT_TIMESTAMP |                |
| updatedAt      | timestamp    | NO   |     | CURRENT_TIMESTAMP |                |
| lastLoginAt    | timestamp    | YES  |     | NULL              |                |
+----------------+--------------+------+-----+-------------------+----------------+
```
- **主键**: id
- **唯一键**: username, email
- **描述**: 存储用户的基础认证信息

## 数据库使用策略

### MySQL 使用场景
- **用户认证信息**: 存储用户的基本账号信息，如用户名、邮箱、密码哈希
- **关系数据**: 存储用户之间的关系，如关注、点赞等
- **结构化数据**: 存储有明确字段定义的数据，如技能、工作经历、教育背景
- **事务性操作**: 需要强一致性保证的场景，如用户注册、数据同步

### MongoDB 使用场景
- **用户档案**: 存储用户详细信息，灵活的文档结构便于扩展
- **文件管理**: 存储用户上传的文件信息，包含丰富的元数据
- **社交内容**: 存储评论、点赞等社交互动数据
- **通知系统**: 存储用户的通知消息，支持灵活的查询

### 混合数据库架构设计原理

在用户注册和登录等核心业务场景中采用混合数据库架构的原因：

#### 1. 数据特性差异
- **MySQL (users 表)**: 存储核心认证数据，具有结构化、强一致性要求的特点
- **MongoDB (users 集合)**: 存储详细用户信息，具有灵活、可扩展的特点

#### 2. 业务场景分析
在用户注册过程中：
- **MySQL**: 存储基本认证信息（用户名、邮箱、密码），提供唯一性约束，作为其他表的外键引用源
- **MongoDB**: 存储用户详细信息，便于后续的查询和更新

#### 3. 实现优势
- **事务与一致性**: MySQL 提供 ACID 特性，确保注册过程的原子性
- **性能优化**: MySQL 优化认证和关系数据查询，MongoDB 优化复杂文档查询
- **灵活性与扩展性**: MongoDB 的模式灵活性允许快速迭代用户功能，MySQL 稳定的结构保证核心业务的可靠性

#### 4. 混合架构优势
- **认证与资料分离**: 核心认证信息使用关系型数据库保证一致性，用户资料使用文档数据库提供灵活性
- **查询优化**: 不同类型的数据使用最适合的数据库进行存储和查询
- **扩展性**: 未来可以独立扩展两个数据库，根据使用场景优化性能

#### 5. 为什么在用户注册和登录中使用混合数据库

**用户注册** (`POST /api/auth/register`) 使用 MySQL + MongoDB 混合架构的具体原因：

- **事务完整性要求**: 注册过程需要保证 MySQL 和 MongoDB 数据的一致性，使用事务确保在任一数据库写入失败时能够回滚
- **核心认证数据**: MySQL users 表存储关键的认证信息（用户名、邮箱、密码），保证唯一性约束和关系完整性
- **用户资料灵活性**: MongoDB users 集合存储用户详细信息，支持未来扩展新的用户属性而无需修改表结构
- **关联ID同步**: 两个数据库都使用相同的 userId，确保数据关联的一致性

**用户登录** (`POST /api/auth/login`) 仅使用 MySQL 的原因：

- **登录验证**: 只需验证用户名/邮箱和密码的正确性，这些核心认证信息都存储在 MySQL users 表中
- **性能优化**: 登录是高频操作，直接在 MySQL 中完成验证可以减少数据库访问次数，提高性能
- **数据一致性**: 认证信息集中在 MySQL 中，避免跨数据库查询带来的复杂性和性能开销

这种设计确保了系统在保持数据一致性的同时，充分利用了不同类型数据库的优势。

### 数据同步策略
- MySQL 作为主数据库，存储核心业务数据
- MongoDB 作为辅助数据库，存储非结构化或半结构化数据
- 通过 userId 字段实现两个数据库间的关联
