# 技术架构文档

## 系统架构概述

这是一个基于 Node.js + Express + MySQL + MongoDB 的个人职业资料管理平台，采用 RESTful API 架构，支持用户注册、登录、个人资料管理、文件上传、社交互动等功能。

## 技术栈

- **后端**: Node.js + Express.js
- **关系型数据库**: MySQL 8.0+
- **文档数据库**: MongoDB 4.0+
- **缓存**: Redis
- **搜索引擎**: Elasticsearch (可选)
- **任务队列**: 未明确使用，可能在 utils 或其他模块中
- **其他**: 环境变量管理 (dotenv), JWT 认证, 文件上传 (multer)

## 数据库设计

### MySQL 数据库 (career_platform)

**表结构关系**:
- `users` 表为核心用户表，其他表通过外键关联此表
- `user_profiles`, `user_skills`, `user_experiences`, `user_education` 等表存储用户扩展信息
- `follows`, `likes`, `comments`, `notifications` 等表处理社交功能
- `user_sessions` 表处理会话管理
- `system_configs` 表存储系统配置

#### 1. users 表 (用户基础信息表)
- **字段**:
  - id (主键, 自增, int)
  - username (用户名, varchar(50), 唯一)
  - email (邮箱, varchar(100), 唯一)
  - passwordHash (密码哈希, varchar(255))
  - avatar (头像URL, varchar(255))
  - createdAt (创建时间, timestamp)
  - updatedAt (更新时间, timestamp)
  - lastLoginAt (最后登录时间, timestamp)

- **用途**: 存储用户的基础认证信息

#### 2. user_profiles 表 (用户档案扩展表)
- **字段**:
  - user_id (外键关联users.id, int, 主键)
  - bio (个人简介, text)
  - location (所在地, varchar(100))
  - website (个人网站, varchar(255))
  - company (公司, varchar(100))
  - position (职位, varchar(100))
  - createdAt, updatedAt

- **外键关系**: 
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **用途**: 存储用户的扩展个人信息

#### 3. user_skills 表 (用户技能表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (外键, int)
  - skill_name (技能名称, varchar(100))
  - proficiency (熟练程度, enum: beginner/intermediate/advanced/expert)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **约束**: `UNIQUE KEY user_skill (user_id, skill_name)`
  
- **用途**: 记录用户掌握的技能及其熟练度

#### 4. user_experiences 表 (用户工作经历表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (外键, int)
  - company (公司名称, varchar(100))
  - position (职位, varchar(100))
  - start_date (开始日期, date)
  - end_date (结束日期, date, 可为空)
  - description (工作描述, text)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **索引**: `KEY idx_user_id (user_id)`
  
- **用途**: 存储用户的工作经历信息

#### 5. user_education 表 (用户教育背景表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (外键, int)
  - school (学校名称, varchar(100))
  - degree (学位, varchar(50))
  - major (专业, varchar(100))
  - start_date (开始日期, date)
  - end_date (结束日期, date)
  - description (教育描述, text)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **索引**: `KEY idx_user_id (user_id)`
  
- **用途**: 存储用户的教育背景信息

#### 6. follows 表 (关注关系表)
- **字段**:
  - id (主键, 自增, int)
  - follower_id (关注者ID, int)
  - following_id (被关注者ID, int)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (follower_id) REFERENCES users(id) ON DELETE CASCADE`
  - `FOREIGN KEY (following_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **约束**: `UNIQUE KEY unique_follow (follower_id, following_id)`
- **索引**: `KEY idx_follower (follower_id)`, `KEY idx_following (following_id)`
  
- **用途**: 记录用户间的关注关系

#### 7. likes 表 (点赞记录表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (用户ID, int)
  - target_type (目标类型, enum: file/comment/post)
  - target_id (目标ID, varchar(24) - MongoDB ObjectId)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **约束**: `UNIQUE KEY unique_like (user_id, target_type, target_id)`
- **索引**: `KEY idx_user (user_id)`, `KEY idx_target (target_type, target_id)`
  
- **用途**: 记录用户对不同资源的点赞行为

#### 8. comments 表 (评论表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (评论者ID, int)
  - target_type (目标类型, enum: file/comment/post)
  - target_id (目标ID, varchar(24) - MongoDB ObjectId)
  - mongodb_id (MongoDB中的评论ID, varchar(24))
  - createdAt, updatedAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **索引**: `KEY idx_target (target_type, target_id)`, `KEY idx_user (user_id)`
  
- **用途**: 存储评论的引用关系，实际评论内容在MongoDB中

#### 9. notifications 表 (通知表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (接收通知的用户ID, int)
  - type (通知类型, enum: like/comment/follow/mention/message/system)
  - title (通知标题, varchar(100))
  - content (通知内容, varchar(500))
  - from_user_id (发送通知的用户ID, int, 可为空)
  - related_type (关联类型, enum: file/comment/profile/message)
  - related_id (关联ID, varchar(24) - MongoDB ObjectId)
  - is_read (是否已读, tinyint(1), 默认0)
  - read_at (阅读时间, timestamp, 可为空)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **索引**: 
  - `KEY idx_user (user_id)`
  - `KEY idx_user_read (user_id, is_read)`
  - `KEY idx_created (createdAt DESC)`
  
- **用途**: 存储用户的通知消息

#### 10. user_sessions 表 (用户会话表)
- **字段**:
  - id (主键, 自增, int)
  - user_id (用户ID, int)
  - token_hash (令牌哈希, varchar(255))
  - expires_at (过期时间, timestamp)
  - createdAt

- **外键关系**:
  - `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
  
- **约束**: `UNIQUE KEY token_hash (token_hash)`
- **索引**: `KEY idx_user (user_id)`, `KEY idx_expires (expires_at)`
  
- **用途**: 存储JWT黑名单，用于控制用户会话

#### 11. system_configs 表 (系统配置表)
- **字段**:
  - id (主键, 自增, int)
  - key (配置键, varchar(100))
  - value (配置值, text)
  - description (配置描述, varchar(255))
  - createdAt, updatedAt

- **约束**: `UNIQUE KEY unique_key (key)`
  
- **用途**: 存储系统的全局配置信息

{

### 数据库使用策略

该项目采用了**混合数据库架构**：
1. **MySQL**: 存储结构化数据和关系数据，如用户基础信息、社交关系、用户技能、工作经历等
2. **MongoDB**: 存储非结构化或半结构化数据，如用户详细资料、文件信息、评论内容等

这种架构结合了关系型数据库的事务一致性和文档数据库的灵活性优势。

### 混合数据库架构设计原理

在用户注册和登录等核心业务场景中采用混合数据库架构的原因：

#### 1. 数据特性差异
- **MySQL (users 表)**: 存储核心认证数据，具有结构化、强一致性要求的特点
- **MongoDB (users 集合)**: 存储详细用户信息，具有灵活、可扩展的特点

#### 2. 业务场景分析
在用户注册过程中：
- **MySQL**: 存储基本认证信息（用户名、邮箱、密码），提供唯一性约束，作为其他表的外键引用源
- **MongoDB**: 存储用户详细信息，便于后续的查询和更新

#### 3. 实现优势
- **事务与一致性**: MySQL 提供 ACID 特性，确保注册过程的原子性
- **性能优化**: MySQL 优化认证和关系数据查询，MongoDB 优化复杂文档查询
- **灵活性与扩展性**: MongoDB 的模式灵活性允许快速迭代用户功能，MySQL 稳定的结构保证核心业务的可靠性

#### 4. 混合架构优势
- **认证与资料分离**: 核心认证信息使用关系型数据库保证一致性，用户资料使用文档数据库提供灵活性
- **查询优化**: 不同类型的数据使用最适合的数据库进行存储和查询
- **扩展性**: 未来可以独立扩展两个数据库，根据使用场景优化性能

#### 5. 为什么在用户注册和登录中使用混合数据库

**用户注册** (`POST /api/auth/register`) 使用 MySQL + MongoDB 混合架构的具体原因：

- **事务完整性要求**: 注册过程需要保证 MySQL 和 MongoDB 数据的一致性，使用事务确保在任一数据库写入失败时能够回滚
- **核心认证数据**: MySQL users 表存储关键的认证信息（用户名、邮箱、密码），保证唯一性约束和关系完整性
- **用户资料灵活性**: MongoDB users 集合存储用户详细信息，支持未来扩展新的用户属性而无需修改表结构
- **关联ID同步**: 两个数据库都使用相同的 userId，确保数据关联的一致性

**用户登录** (`POST /api/auth/login`) 仅使用 MySQL 的原因：

- **登录验证**: 只需验证用户名/邮箱和密码的正确性，这些核心认证信息都存储在 MySQL users 表中
- **性能优化**: 登录是高频操作，直接在 MySQL 中完成验证可以减少数据库访问次数，提高性能
- **数据一致性**: 认证信息集中在 MySQL 中，避免跨数据库查询带来的复杂性和性能开销

这种设计确保了系统在保持数据一致性的同时，充分利用了不同类型数据库的优势。

## 接口设计原则

### 统一响应格式
为了满足您的要求，所有接口应该返回统一的数据格式：
```json
{
  "code": 0,        // 0表示成功，非0表示失败
  "data": {},       // 响应数据
  "msg": "提示信息" // 消息提示
}
```

### 认证机制
- 使用 JWT (JSON Web Token) 进行身份认证
- Token 存储在 HTTP Authorization 头中
- 支持 token 刷新机制
- 使用 Redis 存储 JWT 黑名单以实现登出功能

### 中间件
- `cors`: 处理跨域请求
- `helmet`: 安全头设置
- `compression`: 响应压缩
- `morgan`: 日志记录
- `express-rate-limit`: 限流保护
- `cookie-parser`: Cookie 解析
- `express-validator`: 参数验证
- 自定义 `authenticateToken`: JWT 验证中间件

### 错误处理
- 统一错误处理中间件
- 不同类型错误返回相应的 HTTP 状态码
- 生产环境不暴露敏感信息

## 部署架构

### 数据库部署
- MySQL: 建议使用主从复制或集群模式保证高可用性
- MongoDB: 建议使用副本集或分片集群模式
- Redis: 可使用主从模式或集群模式

### 应用部署
- 单体应用架构
- 支持多进程部署 (使用 PM2 等进程管理器)
- 前后端分离部署

## 性能优化建议

1. **数据库优化**:
   - 合理使用索引
   - 查询优化
   - 读写分离

## 安全措施

1. **认证安全**:
   - 密码使用 bcrypt 加密
   - JWT token 有过期时间
   - 支持 token 刷新和注销

2. **输入验证**:
   - 使用 express-validator 验证输入
   - 防止 SQL 注入和 XSS 攻击
   - 文件上传验证

3. **访问控制**:
   - JWT 认证保护私有接口
   - 用户权限控制
   - API 限流保护
